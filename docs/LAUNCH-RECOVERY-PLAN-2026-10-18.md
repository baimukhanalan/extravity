# Extravity — план восстановления парсинга и подготовки к запуску

Дата фиксации: 18 октября 2026 года. Это план работ, а не отчёт об их выполнении. Текущий статус каждого пункта нужно подтверждать заново перед действием: старые документы описывают другие даты и деплои.

## Точка отсчёта

- Сайт и `/catalog` доступны; в production-базе 11 публичных карточек, из них 5 с будущим дедлайном и 1 активная Telegram-карточка.
- В базе 3 327 неудалённых Telegram-кандидатов. Последний новый кандидат создан 14 октября; последняя зарегистрированная работа Telegram-коннектора — 15 октября.
- У подключённого Railway-сервиса `parser` нет активного деплоя; публичный `/health` возвращает Railway fallback HTTP 404. Причина остановки пока не доказана.
- 10 643 строк `RawSourceItem.failed` относятся к **одному** публичному Telegram-посту из `studygrants`. Записанная ошибка: `unexpected end of hex escape at line 1 column 1123`. Это повторные попытки, не 10 643 разных возможностей.
- Из 3 327 Telegram-кандидатов 3 099 без дедлайна, 2 067 без application URL, 557 без медиа; лишь 3 имеют `moderationStatus=APPROVED`. Эти счётчики пересекаются и не складываются.
- В `apps/parser/channels.yaml` включены 66 каналов; в базе зарегистрировано 58 Telegram-коннекторов. Наличие в конфигурации не доказывает чтение канала или членство аккаунта.
- Локально прошли 711 тестов сайта, 507 тестов парсера и lint; это не production e2e.

## Принципы выполнения

1. Не переносить код или писать что-либо в JOBFINDER и его GitHub-репозиторий. Работать только в Extravity.
2. Не запускать второй процесс с той же Telegram-сессией. Сначала проверить и сохранить состояние постоянного тома, session, курсоры и очередь медиа; не печатать ключи или приватные сообщения в отчётах.
3. Не сдвигать Telegram-курсор до подтверждённого приёма или долговременной карантинной записи. Не считать HTTP 200 с `failed > 0` успешной обработкой пачки.
4. Не публиковать массово непроверенные записи. Источник, сроки, школьная аудитория, подача и оригинальное медиа должны иметь проверяемое основание. Внешняя ссылка может быть скрыта от ученика, но остаётся во внутреннем provenance.
5. Ни тесты, ни успешный деплой сами по себе не равны живому пользовательскому результату. Для каждого этапа проверять код, runtime, данные и публичную страницу отдельно.

4. Поднять исправленный сервис сначала в режиме контролируемого canary: `/health` должен вернуть JSON сервиса, Telegram session — `connected`, media storage — ready, preflight сайта — успешен. Затем выполнить один ограниченный dry-run и один разрешённый ingest.

**Откат:** выключить live-сбор, сохранить том и логи; не сбрасывать session/state и не запускать массовый backfill на неисправном образе.

## P0. Устранить «ядовитый» пост и ложный успех заданий

**Метод**

1. Изолировать одну неуспешную запись по `contentHash`/URL и воспроизвести `prisma.opportunity.create()` на безопасной копии данных либо в откатываемой тестовой транзакции. Уменьшать payload по полям до конкретной последовательности, которая вызывает ошибку. Не выводить весь текст поста и медиа в логи.
2. Исправить первопричину в нормализации/сериализации или сохранении JSON и добавить регрессионный тест с минимальным воспроизводящим фрагментом. Не «лечить» проблему удалением поста или ручным переносом курсора.
3. Разделить исходы ingest: `created`, `duplicate`, `expired`, `quarantined`, `failed`. Если хотя бы одна запись не сохранена, `ParserJob` должен быть `partial_failure`/`failed`, а не `completed`; ответ API и метрики должны отражать это.
4. Для постоянной ошибки после ограниченного числа повторов сохранять пост и причину в долговременный карантин с уникальным ключом, а не создавать бесконечные `RawSourceItem.failed`. Карантин должен поддерживать повтор после исправления и не блокировать другие каналы.
5. Повторить именно этот пост, затем ту же пачку повторно: первая обработка создаёт максимум одну возможность, повторная — идемпотентный дубль; ошибки больше не размножаются.

**Критерий готовности:** один пост больше не создаёт поток одинаковых ошибок; частичный сбой виден оператору; другие каналы продвигаются; исходный пост не потерян.

## P1. Аудит покрытия 66 Telegram-источников

**Метод**

1. Сопоставить `channels.yaml` с фактически доступными аккаунту каналами, `SourceConnector`, последним успешным чтением, курсором и последним постом. Статусы: `connected`, `not_joined`, `inaccessible`, `flood_wait`, `empty`, `error`, `disabled`.
2. Для восьми источников без коннектора определить точную причину по read-only dry-run. Не считать их автоматически «неподписанными»: возможны пустой результат, фильтр, недоступность или отказ ingest.
3. Для каждого доступного канала выполнить ограниченный прогон с паузами и официальными ограничениями Telegram. Считать просмотренные посты, отброшенные как не-возможность, исключённые по аудитории, кандидаты, дубли, ошибки медиа и ошибки ingest.
4. Сохранить единую таблицу покрытия в эксплуатационном отчёте. Добавлять новые источники только после проверки тематической доли, актуальности, доступа и допустимости использования.

**Критерий готовности:** у каждого из 66 источников есть объяснимый текущий статус и дата последней проверки; ни один не обозначен «работает» только по записи в YAML.

## P1. Повысить качество извлечения условий

**Метод**

1. Собрать размеченный набор реальных постов из разных языков и форматов: открытый набор, итоги, реклама, студенческая программа, афиша с датой, ссылка на положение, несколько дат, неизвестная цена. Разделить его на обучение правил и независимую проверку.
2. Зафиксировать для каждого поля происхождение: текст поста, Telegram entity URL, исходное изображение/документ, официальная страница организатора. OCR добавлять только для допустимых материалов и с сохранением ссылки на оригинал; найденное OCR значение не считать подтверждённым без сверки контекста.
3. Доработать дедлайны: различать старт и конец приёма, дату события и дату публикации; учитывать часовой пояс Алматы и год исходного поста; при противоречии хранить обе версии и блокировать автоматическую публикацию.
4. Проверять application URL как реальный путь подачи, а не просто первую ссылку. Для цены различать `0 подтверждено`, `известная сумма` и `стоимость не указана`; последнее показывать как «Стоимость уточняется у организатора», без утверждения «бесплатно».
5. Сверять школьную аудиторию и доступность для Казахстана по актуальным правилам организатора; агрегаторский канал не считать организатором без основания. Исправления модератора превращать в регрессионные примеры.
6. Измерять precision и recall на отложенной выборке отдельно для типа возможности, дедлайна, аудитории, application URL и цены. Порог автопубликации определять по ложным публикациям, а не по общему проценту заполненных полей.

**Критерий готовности:** каждое заполненное критическое поле имеет источник; ложные школьные и ложные будущие дедлайны не проходят gate; качество подтверждено на выборке, не участвовавшей в настройке правил.

**Критерий готовности:** сутки наблюдения с измеренными задержками, корректными тревогами и доказанным восстановлением после restart.
