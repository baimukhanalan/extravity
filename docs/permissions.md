# Роли и доступы (RBAC)

Роль хранится в `User.role` (enum `Role`) и в подписанном JWT-сессии. Проверки — **на сервере**.

## Роли

| Роль | Доступ |
|---|---|
| `STUDENT` | Свой профиль, каталог, рекомендации, сохранения, заявки, документы, достижения, портфолио, отправка ссылок |
| `PARENT` | (заложено) Связь с ребёнком, согласия, статусы заявок, подписка |
| `COUNSELOR` | (заложено) Ученики школы при согласии, подборки, назначения, отчёты |
| `ORGANIZER` | (заложено) Профиль организации, публикация после модерации, заявки на свои возможности |
| `MODERATOR` | Модерация ссылок и возможностей, изменение данных |
| `ADMIN` | Полный доступ к админ-панели |
| `SUPER_ADMIN` | Всё + критические настройки |

## Механизм проверки

`lib/auth.ts`:

- `getSession()` — читает и верифицирует JWT из httpOnly-cookie.
- `requireUser()` — редиректит на `/login`, если нет валидной сессии; возвращает пользователя.
- `requireRole([...])` / `requireAdmin()` — проверяют роль, иначе редирект.

Применение:

- `app/app/layout.tsx` → `requireUser()` — портал только для авторизованных.
- `app/admin/layout.tsx` → `requireAdmin()` — админка только для staff-ролей.
- Server Actions дополнительно вызывают `requireUser()` / `requireAdmin()` и проверяют,
  что объект принадлежит пользователю (например, `application.findFirst({ where: { id, userId } })`)
  — защита от IDOR.

## Принципы

- Права проверяются на сервере при каждом запросе и мутации — **не** через скрытие кнопок во фронте.
- Пользователь работает только со своими данными (владение проверяется в запросах).
- Все чувствительные действия пишутся в `audit_logs` (вход, смена статусов, модерация, согласия и т.д.).
- Row Level Security на уровне БД — следующий шаг при переходе на Supabase/пул с ролями
  (сейчас изоляция обеспечивается серверными проверками владения).
