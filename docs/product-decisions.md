# Продуктовые и технические решения

Формат: **что сделано → почему → ограничения → что осталось для production.**

## 1. Единый Next.js вместо микросервисов на старте
- **Что:** вся бизнес-логика — в Next.js (Server Actions + Route Handlers), данные — Prisma + Postgres.
- **Почему:** соответствует «предпочтительному варианту» ТЗ; быстрее до рабочего продукта; один деплой.
- **Ограничения:** тяжёлый парсинг и очереди не место в serverless-функциях.
- **Production:** отдельные `apps/parser-api` (FastAPI) и `apps/worker` (Celery/Redis) для сбора данных.

## 2. Prisma 6, а не 7
- **Что:** откат с установленной Prisma 7 на 6.
- **Почему:** Prisma 7 требует driver adapters и `prisma.config.ts`; на старте это лишний риск. Prisma 6 стабильна и проверена на Vercel.
- **Production:** миграция на 7 при необходимости, с адаптером Neon serverless.

## 3. Собственная auth вместо Supabase Auth
- **Что:** email+пароль (bcrypt) + JWT-сессия в httpOnly-cookie.
- **Почему:** полный контроль, отсутствие внешней зависимости на старте, работает на любом Postgres.
- **Ограничения:** нет готового OAuth/MFA/passwordless из коробки.
- **Production:** MFA для админов, passwordless/OAuth, session revocation; при переходе на Supabase — их Auth + RLS.

## 4. Авторизация в серверных layout'ах, а не в middleware
- **Что:** `requireUser/requireAdmin` в layout'ах и экшенах.
- **Почему:** в Next 16 `middleware` переименован в `proxy`; серверная проверка ближе к данным и надёжнее.

## 5. Neon (пул + прямой URL)
- **Что:** прод-БД — Neon serverless Postgres; рантайм через пул с `pgbouncer=true`, миграции — через прямой URL.
- **Почему:** бесшовно с Vercel, free tier, serverless-дружелюбно.
- **Нюанс:** без `pgbouncer=true` Prisma ломается на prepared statements в transaction-pooling.

## 6. Match / Trust / Eligibility как чистые функции
- **Что:** `lib/eligibility.ts`, `lib/match.ts` — сначала жёсткие фильтры (возраст/класс/город/язык/бюджет/дедлайн),
  затем взвешенный match score с объяснениями; ineligible ограничен сверху.
- **Почему:** прозрачность и тестируемость; match — рекомендательная оценка, без ложной точности.
- **Production:** добавить embedding-similarity для дубликатов и тегов; A/B весов.

## 7. Локализация
- **Что:** UI на русском (основная аудитория) со структурой под ru/kk/en; переключатель языка сохраняет выбор в профиле; хранение исходного языка и `availableLanguages` у возможностей.
- **Ограничения:** полный перевод всех строк на kk/en не завершён.
- **Production:** `next-intl` со словарями и сохранёнными переводами возможностей в БД (без генерации на каждый рендер).

## 8. Документы, платежи, парсер — помечены как mock
- **Документы:** метаданные хранятся, файл эмулируется (`isMock`). Production — Storage + signed URL.
- **Платежи:** database-driven entitlements + абстрактный «mock provider»; реальный эквайринг (Halyk/Kaspi/CloudPayments) подключается за интерфейсом.
- **Источники/парсер:** страница источников показывает конфигурацию; запуски эмулированы. Реальный сбор — в Python-сервисе, с соблюдением robots.txt/rate limits и без обхода защиты.

## 9. Что осознанно НЕ вошло в первую версию (по ТЗ, раздел 46)
Соцсеть, публичный рейтинг школьников, общий чат, маркетплейс репетиторов, собственные курсы,
массовый серый скрейпинг Instagram/Telegram, мобильные приложения,
блокчейн/токены, сложная геймификация, AI, выдумывающий достижения, гарантии поступления,
автосписания без явного согласия. Архитектура учитывает будущее, но это не блокирует запуск.

## 10. Разделение аккаунтов при деплое (операционное)
- **Что:** приложение задеплоено под аккаунтом Vercel, в котором был авторизован CLI; БД Neon создана в основном аккаунте пользователя; связь — через `DATABASE_URL`.
- **Почему:** так было быстрее и надёжнее в конкретной среде; строка подключения Neon самодостаточна.
- **Production:** свести БД и приложение в один аккаунт/команду Vercel для единого биллинга и управления.
