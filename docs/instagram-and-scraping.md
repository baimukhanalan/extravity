# Instagram, веб-скрапинг и границы автоматического сбора

Документ отвечает на три вопроса: почему сбор из Instagram устроен иначе, чем из
Telegram, какими легальными путями он всё-таки реализован (Graph API по хештегам
и пересылка поста боту), и как работает веб-скрапер проекта. Скрапинг Instagram
в обход защиты сознательно **не** реализован — почему, разобрано ниже.

---

## 1. Почему Telegram можно читать программой, а Instagram — нет

Разница не в сложности, а в том, что платформа сама разрешает.

| | Telegram | Instagram |
|---|---|---|
| Протокол для сторонних клиентов | MTProto, **документирован** | нет |
| Ключи разработчика | `api_id`/`api_hash` выдаёт сама платформа на my.telegram.org | только Graph API под конкретные сценарии |
| Автоматическое чтение публичного контента | штатный клиентский сценарий | запрещено условиями использования |
| Что нужно, чтобы это работало | соблюдать серверные лимиты (`FloodWait`) | обходить антибот-защиту |

Ключевая строка — последняя. Telethon работает **благодаря** соблюдению правил:
получил `FloodWait` — подождал. Скрапер Instagram работает только **вопреки**
защите, и живёт ровно до момента, пока защита его не распознает. Разница не
юридическая формальность, а разное инженерное содержание задачи.

Поэтому в проекте реализован сбор из Telegram и не реализован из Instagram.

---

## 2. Как вообще устроена защита от автоматического сбора

Это защитная сторона темы — что и почему детектируют. Понимание нужно и тем, кто
строит парсеры (чтобы понимать, где проходит граница дозволенного), и тем, кто
защищает свой сервис.

Детектирование работает слоями, и суть в том, что **обмануть один слой мало**:
слои перекрёстно проверяют друг друга.

**Сетевой уровень.** У TLS-рукопожатия есть отпечаток: набор и порядок
поддерживаемых шифров, расширений, эллиптических кривых. У HTTP/2 — свой:
параметры SETTINGS, порядок псевдозаголовков, схема приоритетов. Эти отпечатки
задаёт библиотека, а не заголовок `User-Agent`. Классическая находка защиты —
клиент, который представляется браузером, но имеет отпечаток HTTP-библиотеки.
Противоречие между заявленным и наблюдаемым и есть сигнал.

**Уровень клиента.** Браузер выдаёт сотни измеримых свойств: разрешение экрана,
часовой пояс, набор шрифтов, параметры отрисовки Canvas и WebGL, версии кодеков.
Совокупность даёт устойчивый идентификатор. Отдельно ловится «слишком чистая»
среда — свойства, характерные для headless-режима.

**Поведенческий уровень.** Человек читает с паузами, промахивается мимо ссылок,
двигает мышь по кривой, скроллит неравномерно. Автомат обходит страницы с
одинаковыми интервалами, идеально попадает в элементы и никогда не возвращается
назад. Здесь же — соотношение просмотров к действиям и время на странице.

**Уровень репутации.** IP-адрес имеет историю: датацентр или домашний провайдер,
были ли с него нарушения. Аккаунт имеет возраст, заполненность профиля, историю
активности. Свежий аккаунт из подсети датацентра подозрителен ещё до первого
запроса.

**Ловушки.** Ссылки, невидимые человеку (скрытые CSS), но видимые парсеру
разметки; поля-приманки в формах; страницы, упомянутые в `robots.txt` как
запрещённые. Обращение к ним — почти достоверный признак автомата, потому что у
обычного пользователя нет способа туда попасть.

**Реакция** обычно ступенчатая: замедление, затем дополнительная проверка,
требование входа, затем блокировка IP или аккаунта. Ступенчатость намеренная — она делает
подбор обхода дорогим и заметным.

Вывод, который стоит зафиксировать в работе: устойчивость такой защиты держится
не на одном хитром приёме, а на **согласованности множества независимых
сигналов**. Именно поэтому обход — это не разовая задача, а бесконечная гонка, и
именно поэтому легальные каналы доступа (API, партнёрство) на дистанции дешевле.

## 3. Легальные пути для Instagram (реализованы)

**a) Graph API, поиск по хештегу** — `apps/parser/igcollect/`. Официальный и
единственный поддерживаемый способ читать чужие публичные посты:
`ig_hashtag_search` возвращает id хештега, `recent_media` — недавние публичные
посты по нему. Нужны Business- или Creator-аккаунт, приложение в Meta for
Developers и ревью с обоснованием сценария. Ограничения самого API: только
хештеги (не произвольные аккаунты), квота на число уникальных хештегов за 7 дней,
отдаётся подмножество полей.

Что заложено в код (`igcollect/client.py`, `pipeline.py`):

- запрашиваются **только публичные, не персональные** поля — `caption`,
  `permalink`, `timestamp`, `media_type`; ни имён пользователей, ни подписчиков;
- без токена (`IG_ACCESS_TOKEN` + `IG_BUSINESS_ID`) коллектор к сети не ходит;
  production automation дополнительно требует `IG_APP_ID` + `IG_APP_SECRET`,
  проверяет токен официальным `/debug_token`, Meta app, permissions, срок
  действия и добавляет `appsecret_proof` к Graph-запросам:
  `credentials_ready()` False, и CLI запускает офлайн-фикстуру;
- caption разбирается **тем же** экстрактором, что и посты Telegram
  (`tgcollect.extract`), и уходит в ту же очередь модерации;
- id хештега кэшируется на прогон, между хештегами пауза.

Демонстрация без Business-аккаунта — на встроенном примере ответа Graph API
(`igcollect/demo.py`, форма 1-в-1 с настоящим `recent_media`):

```bash
cd apps/parser
python run_instagram.py --demo            # разбор фикстуры, без сети и токена
python run_instagram.py --demo --no-llm   # только регулярки
python run_instagram.py --dry-run         # с токеном: запрос хештегов без отправки
```

**b) Поделиться постом → бот** — `app/api/telegram/webhook/route.ts`. Instagram
не пересылается в Telegram как нативный форвард, поэтому человек вставляет боту
текст поста вместе со ссылкой `instagram.com/p/...`. Бот распознаёт ссылку
(`instagramPermalink` в `lib/opportunity-extract.ts`), приводит reel/tv/www к
канонической форме `https://www.instagram.com/p/<id>/` (одинаковый ключ
дедупликации), разбирает caption тем же `extractCandidate` и кладёт в очередь
модерации с типом источника `instagram_forward`. Работает с любым аккаунтом, не
требует прав, человек в цикле.

**c) Организаторы публикуют сами** — кабинет организатора (`/organizer`) с
верификацией. Самый качественный источник: организатор сам следит за
актуальностью своей карточки.

## 4. Веб-скрапер проекта

Живёт в `apps/parser`. Что уже соблюдается в коде (`parser/fetch.py`):

- **`robots.txt`** проверяется перед каждым хостом, результат кэшируется;
  запрет означает отказ от загрузки, а не обход;
- **пауза между запросами** к одному хосту (по умолчанию 2 секунды);
- **честный `User-Agent`** с названием проекта и ссылкой — чтобы администратор
  сайта мог понять, кто к нему ходит, и связаться;
- никаких попыток получить неразрешённый доступ к защищённым данным.

### Три уровня разбора

Порядок задан тем, насколько данные буквальны (`parser/pipeline.py`):

1. **schema.org JSON-LD** — организатор указал поля явно. Берём как есть.
2. **Текст страницы** — регулярки плюс необязательное уточнение моделью. Тот же
   двухслойный экстрактор, что и для постов Telegram. Это уровень для страниц
   «Положение о конкурсе», у которых разметки нет вовсе, — а таких большинство.
3. **OpenGraph/meta** — заголовок и описание; последний рубеж, чтобы страница
   хотя бы попала в очередь модерации.

Правило то же, что при слиянии ответа модели: значение, опубликованное в
машиночитаемом виде, всегда важнее выведенного из прозы.

Отдельная деталь второго уровня: на веб-странице ссылка на регистрацию лежит в
атрибуте `href`, а не в тексте. Поэтому `page_text()` собирает адреса ссылок и
дописывает их к тексту — иначе фраза «Заполните форму регистрации» приходит без
самой формы. Это ровно та же проблема, что скрытые за подписью ссылки в постах
Telegram, и решается она так же.

```bash
cd apps/parser
python run.py --dry-run                 # все включённые источники, без отправки
python run.py --dry-run --no-llm        # только регулярки
python -m pytest tests -q               # 51 тест, включая фикстуру без разметки
```

## 5. Что считать допустимым сбором

Рабочий критерий, которым удобно проверять любой новый источник:

1. **Разрешает ли платформа** читать это программой — прямо или через API?
2. **Соблюдаются ли объявленные ограничения** — `robots.txt`, лимиты, паузы?
3. **Продолжит ли это работать, если ничего не скрывать** — если для
   работоспособности нужно маскироваться, ответ на пункт 1 был «нет».
4. **Минимальны ли данные** — берём только то, что нужно каталогу: текст
   объявления и ссылку, без сведений об авторах и подписчиках?
5. **Есть ли человек в цикле** перед публикацией?

Все реализованные источники проходят все пять пунктов: Telegram-коллектор,
веб-скрапер, Instagram через Graph API и пересылку поста боту. Скрапер Instagram
в обход защиты не проходит первый и третий — поэтому его в проекте нет, а вместо
него сделаны два легальных пути из раздела 3.

| Источник | 1. разрешён | 2. лимиты | 3. без маскировки | 4. мин. данные | 5. модерация |
|---|:-:|:-:|:-:|:-:|:-:|
| Telegram (MTProto) | ✅ | ✅ FloodWait | ✅ | ✅ | ✅ |
| Веб-скрапер | ✅ | ✅ robots.txt | ✅ | ✅ | ✅ |
| Instagram Graph API | ✅ | ✅ квоты | ✅ | ✅ | ✅ |
| Пересылка поста боту | ✅ | — | ✅ | ✅ | ✅ |
| Скрапинг Instagram | ❌ | — | ❌ | — | — |
