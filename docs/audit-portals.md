# Аудит порталов: userflow, workflow, доступ

Дата: 2026-08-08. Проверено: гарды доступа (код), владение ресурсами (IDOR),
основные userflow (e2e Playwright + ручная проверка).

## Метод

- **Гарды.** Каждая страница портала и каждое server-action проверены на вызов
  `requireX`. Layout защищает страницы; **actions защищаются отдельно** (они —
  самостоятельные POST-эндпоинты, layout их не покрывает).
- **IDOR.** Все действия, принимающие `id`, проверены на скоуп по владельцу.
- **e2e.** 3 сквозных сценария в `e2e/` гоняются в CI против реального билда+БД.

## 1. Портал школьника (`/app`, роль STUDENT)

**Страницы (16):** главная, лента (discover), рекомендации, сохранённое,
календарь, заявки + workspace `[id]`, документы, портфолио, достижения, «нашёл
возможность», уведомления, профиль, подписка, настройки, онбординг.

**Userflow (e2e `registration.spec.ts`):** регистрация → онбординг (можно
пропустить) → главная с лентой → каталог → карточка → «Начать подготовку» →
workspace заявки. ✅ проходит.

**Доступ:** layout `requireUser`. Не-школьники (staff/organizer/…) редиректятся
логином в свой портал. Заявки/документы/сохранённое скоупятся `where userId`
(`findFirst`), чужие недоступны. ✅

**Workflow оплаты (e2e `payment.spec.ts`):** подписка → «Выбрать (демо)» →
mock-провайдер закрывает сразу → план становится текущим. ✅

## 2. Админка (`/admin`, роль MODERATOR/ADMIN/SUPER_ADMIN)

**Страницы (13):** обзор, модерация, возможности + new, **покрытие** (новое),
отправки, пользователи, организаторы, жалобы, источники, задачи парсера, флаги,
аудит.

**Workflow модерации (e2e `moderation.spec.ts`):** школьник отправляет ссылку →
модератор видит в очереди → «Одобрить» → ссылка уходит из очереди. ✅

**Доступ:** layout `requireAdmin` (STAFF-роли). Все admin-actions
(`createOpportunity`, `reviewSubmission`, `reviewOrganizer`, `toggleFeatureFlag`,
`toggleUserActive`, `setOpportunityStatus`) независимо зовут `requireAdmin`. ✅

**Покрытие категорий (новое):** по 20 категориям — активные/с дедлайном/последнее
пополнение/источники, сортировка «худшие сверху» (дефицит → устаревание → норма).

## 3. Портал организатора (`/organizer`, роль ORGANIZER)

**Страницы:** регистрация, обзор, мои возможности + new + `[id]`, заявки,
профиль организации.

**Userflow:** регистрация организации → PENDING-верификация → создание
возможности (→ PENDING_REVIEW, модерация) → правка → аналитика заявок.

**Доступ:** `requireOrganizer` (гейт — наличие записи `Organizer`, иначе редирект
на `/organizer/register`). Возможности скоупятся `organizerId !== organizer.id`
на update/status. По заявкам — **только агрегат**, когорты <3 человек скрыты
(защита ПДн школьников). ✅

## 4. Портал куратора (`/counselor`, роль COUNSELOR)

**Страницы:** регистрация, обзор, ученики + `[id]`, профиль, приглашение
`invite/[token]`.

**Userflow:** регистрация → приглашение ученика по email → **ученик сам
принимает** (`/counselor/invite/[token]`) → куратор видит профиль/заявки/
достижения → рекомендация возможности.

**Доступ:** `requireCounselor`. Страница ученика `students/[id]` скоупится по
**активной связи** (`counselorId + studentUserId + status:"active"`), не по id из
URL. Ученик отзывает доступ из настроек. ✅ — ключевая приватность соблюдена.

## 5. Портал родителя (`/parent`, роль PARENT/любой с активной связью)

**Страницы:** no-access, обзор, дедлайны, согласия, consent по токену.

**Userflow:** школьник приглашает родителя из настроек → письмо со ссылкой →
родитель подтверждает согласия (по токену или в кабинете) → видит детей,
дедлайны, плановые расходы, управляет согласиями с **немедленным отзывом**.

**Доступ:** `requireParent` (гейт — наличие активной/pending связи
`ParentStudentLink.parentUserId`, иначе `/parent/no-access`). `setConsent`/
`revokeParentLink` работают только со связями из `requireParent` (нельзя тронуть
чужую). Родителю видны заявки/дедлайны/стоимость — **не** документы и черновики. ✅

Дыр доступа не найдено. Кросс-портальная модель едина: доступ к чужому профилю
всегда через **активную связь**, а не идентификатор в URL; демо-креды на прод не
засеяны.

## Новые фичи (рычаги) в userflow

- **Удержание.** Ученик в ленте задаёт фильтр → «Сохранить поиск» → на
  `/app/saved` управляет поисками и алертами; ежедневный cron шлёт новые
  совпадения, недельный дайджест — по понедельникам; в настройках — включение
  push в браузере. e2e: сохранение поиска.
- **Конверсия.** В workspace заявки — AI «обратная связь по эссе» (за флагом) и
  комментарии; куратор/родитель по активной связи комментируют черновик, ученику
  приходит уведомление. Доступ к комментариям — через `resolveAccess`.
- **Доверие.** На карточке возможности — «Результаты участников»: счётчики
  подали/прошли + анонимные отзывы; ученик отмечает свой исход. Сортировка
  каталога «по результатам». e2e: отзыв об исходе.
- **Портфолио.** В портфолио — тумблер публичной ссылки (за флагом); публичная
  страница `/p/[slug]` показывает достижения без персональных данных, `noindex`.

Проверено e2e (5 сценариев, все зелёные) + ручной разбор доступа новых поверхностей
(см. `docs/security-audit.md`, раздел «Новые поверхности»).
